# Phase 4 설계 - 수집 에이전트 · 이상 탐지 · 알림

작성 2026-09-14. 지금까지는 사용자가 소스 ZIP·로그 파일을 직접 올려 분석했다.
이번 단계는 서버에 설치한 에이전트가 로그와 자원 지표를 계속 보내고,
플랫폼이 이상을 찾아 담당자에게 알리는 흐름을 만든다.

```
[서버] Agent ──HTTPS(배치, 토큰)──▶ Spring Boot /api/ingest ──▶ 저장소
                                         │                       │
                                         ├─▶ 알림 규칙 평가 ─▶ Slack / Naver Works / SMS / Redmine
                                         └─▶ Python 분석 서비스 (이상 탐지, 로그 패턴, LLM 요약)
```

호출 방향 원칙은 그대로다. 화면은 백엔드만 부르고, 에이전트도 백엔드로만 보낸다.

---

## 1. 에이전트

| 항목 | 내용 |
| --- | --- |
| 역할 | 로그 파일 tail, 시스템 지표(CPU·메모리·디스크·네트워크) 수집, 배치 전송 |
| 설치 | 단일 설치 파일 + 설정 파일(`%ProgramData%\MonitoringAgent\agent.json`), Windows 서비스 등록 |
| 인증 | 에이전트별 토큰 (화면에서 발급·삭제, 서버에는 SHA-256 해시만 저장). 요청 헤더 `X-Agent-Token` |
| 전송 | 10초 또는 500건마다 gzip JSON 배치. 실패하면 로컬 디스크 버퍼 후 재전송 |
| 상태 | 30초마다 heartbeat. 2분 넘게 끊기면 "연결 끊김" 이벤트와 알림 |

설정 예 (자세한 내용은 `agent/README.md`):

```json
{
  "server": "https://monitoring.example.com",
  "token": "agt_xxxxx",
  "logs": [{ "path": "C:\\app\\logs\\*.log" }],
  "metricsIntervalSeconds": 15
}
```

## 2. 수집 API (백엔드)

```
POST /api/ingest/logs       에이전트 로그 배치
POST /api/ingest/metrics    에이전트 지표 배치
POST /api/ingest/heartbeat
GET  /api/projects/{id}/agents          에이전트 목록·상태
POST /api/projects/{id}/agents          토큰 발급 (토큰 원문은 이때 한 번만 보여줌)
DELETE /api/projects/{id}/agents/{agentId}
```

- 토큰은 해시로만 저장한다.
- 요청당 최대 5MB, 에이전트별 초당 요청 제한.
- Syslog(UDP/TCP 514)·MQTT·Kafka 입력은 같은 내부 수집 서비스로 모이도록 어댑터만 추가한다.

## 3. 저장

| 데이터 | 1차 저장소 | 보존 |
| --- | --- | --- |
| 로그 원문 | MySQL 일 단위 파티션 테이블 `log_entry` | 14일 |
| 지표 | MySQL `metric_point` (1분 집계) | 30일, 이후 1시간 집계 1년 |
| 이상 탐지 결과·알림 이력 | MySQL | 1년 |

데이터가 커지면 로그는 ClickHouse / OpenSearch, 지표는 TimescaleDB 로 옮긴다.
수집 API 뒤에 저장소 인터페이스를 두어 교체해도 화면·에이전트는 바뀌지 않게 한다.

## 4. 이상 탐지 (Python)

단계적으로 붙인다. 앞 단계만으로도 쓸 수 있어야 한다.

1. **규칙 기반**: 오류율, 치명 로그 발생, 응답 지연 임계치, 디스크 사용률
2. **통계 기준선**: 요일·시간대별 평균과 편차로 급증·급감 탐지 (z-score, EWMA)
3. **로그 패턴**: 기존 오류 묶기 로직을 확장해 "처음 보는 오류 유형" 감지
4. **LLM 요약**: 이상 구간의 로그·지표를 요약하고 가능한 원인과 확인할 곳을 제안
   (민감정보 마스킹 후 전송, 사용 여부는 프로젝트 설정에서 켜고 끔)

## 5. 알림

- 알림 규칙: 조건(이상 유형, 심각도, 지속 시간) + 대상 채널 + 조용한 시간
- 같은 이상은 묶어서 한 번만 보낸다(중복 억제 10분), 해결되면 해결 알림
- 채널 어댑터: Slack(Webhook), Naver Works(Bot API), SMS(사내 게이트웨이 또는 외부 발송사), Redmine(이슈 생성)
- 모든 발송은 이벤트 화면에 기록한다

## 6. 화면

- 프로젝트 > 에이전트 탭: 설치 안내, 토큰 발급, 연결 상태
- 모니터링: 서버별 CPU·메모리·디스크 추이, 실시간 로그 스트림(최근 N줄)
- 이벤트: 이상 탐지·알림 발송 기록 추가
- 설정 > 알림: 채널 연결, 규칙 편집, 테스트 발송

## 7. 진행 순서

| 단계 | 내용 | 결과물 |
| --- | --- | --- |
| 4-1 | 에이전트 토큰·수집 API·저장 테이블 | 로그·지표가 쌓이고 모니터링 화면에 보임 |
| 4-2 | 에이전트 1차 (로그 tail, 지표, heartbeat) | 실제 서버에 설치 가능 |
| 4-3 | 규칙·통계 기반 이상 탐지 | 이벤트 화면에 이상 기록 |
| 4-4 | 알림 채널 1개 + 규칙 화면 | 담당자에게 실제 알림 |
| 4-5 | 나머지 채널, LLM 요약, Syslog/MQTT/Kafka 어댑터 | 전체 기능 |

## 8. 결정 사항 (2026-09-14)

1. 에이전트: C# .NET 8. 설치·트레이 화면은 기존 사내 에이전트와 같은 토스형 디자인, 수집은 Windows 서비스
2. 전송: HTTPS 직접 전송 (gzip JSON 배치)
3. 저장: 기존 DB(H2 로컬 / MySQL)의 `log_entry`, `metric_point` 테이블. 파티션·전용 저장소는 데이터가 커지면
4. 첫 알림 채널: Slack Incoming Webhook
5. LLM 요약: 나중에 결정. 백엔드 `IncidentInsight` 인터페이스로 연결 지점만 둠

## 9. 진행 현황

| 단계 | 상태 | 구현 위치 |
| --- | --- | --- |
| 4-1 | 완료 | `backend/.../agent`, `ingest`, `telemetry` · 프로젝트 에이전트 탭 · 실시간 로그 · 모니터링 서버 자원 |
| 4-2 | 완료 | `agent/` (Worker 서비스 + WPF 설치/트레이, 설치 파일 `dist/MonitoringAgentSetup.exe`) |
| 4-3 | 완료 | `backend/.../incident` (규칙) + `service/app/analysis/anomaly.py` (추세) · 모니터링 이상 탐지 카드 |
| 4-4 | 완료 | `backend/.../alert` · 설정 > 알림 (채널, 규칙, 테스트 발송, 발송 기록) |
| 4-5 | 남음 | Naver Works / SMS / Redmine, LLM 요약, Syslog·MQTT·Kafka, Linux 에이전트 |

이상 탐지 규칙 (1분 주기, 기준값은 `app.detection.*`):

| 유형 | 조건 | 심각도 | 해결 |
| --- | --- | --- | --- |
| 에이전트 연결 끊김 | 2분 넘게 신호 없음 | 심각 | 다시 신호가 오면 |
| CPU·메모리 사용률 높음 | 5분 평균 90% 이상 (97% 이상 심각) | 주의/심각 | 80% 미만 |
| 디스크 사용률 높음 | 90% 이상 (95% 이상 심각) | 주의/심각 | 85% 미만 |
| 오류 로그 급증 | 5분 동안 ERROR·FATAL 20건 이상 (100건 이상 심각) | 주의/심각 | 10건 미만 |
| 치명 로그 발생 | FATAL 로그 수신 | 심각 | 10분 동안 없으면 |
| 처음 보는 오류 | 이전에 없던 오류 메시지 유형 (수집 1시간 이후부터) | 주의 | 30분 뒤 |
| 오류·CPU 추세 이상 | 최근 5분 값이 평소(EWMA) 대비 크게 벗어남 (Python) | 주의 | 벗어남이 사라지면 |
